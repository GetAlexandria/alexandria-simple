The Core Trifecta

Alexandria's core product is three things, with a fourth implied:

Agents
+
Plays
+
Context Library
+
Orchestration
"Without relevant, up-to-date organizational context, this is fairly tone-deaf."
— Danvers, Apr 9

The context library is what makes the agents and plays valuable. Orchestration is what makes the plays run. Everything else (CLI, web viewer, agent play, settings) is a multiplier — not core.

Decision — Reversal

We Own Orchestration

Day 1 Position (Superseded)

"The orchestrator is outside... we're delegating the solution to this one platform or these three platforms."

↓

Day 2 Position (Settled)

"If the plays are the secret sauce, how the plays are orchestrated is part of the secret sauce. We have to run the plays."

The nuance:

  • Bundle an open-source orchestration framework — don't build one
  • Individual agents + skills can still run on external harnesses (Claude Code, OpenClaw)
  • Plays specifically require orchestration and run inside the library
  • The execution infrastructure (durability, cost control, restarts) comes from the bundled framework

new card Artifact — Decision: Orchestration Ownership

Principle

The Sandwich

Agentic → Deterministic → Agentic

Agentic — Outer Interface & orchestration across the whole workflow
Raven
Deterministic — Middle Workflow on rails — constrains what agents can do
Plays, Skills, Software gates
Agentic — Inner Individual tasks within workflow structure
Sam, Conan, Nit, Solomon, Bridget
"This is the pattern I've seen in all the agentic systems we've built."
— Jess, Apr 9
  • Settled as a principle, not a hard requirement
  • The outer agentic layer can work around things the workflow can't handle
  • The deterministic middle can wrap both deterministic and non-deterministic stations
  • This is what makes Raven magical — constrained by the workflow but not trapped by it

The S Boundary

What is inside vs. outside the minimum valuable product?

Inside S

  • Agents (the team)
  • Plays (procedural knowledge)
  • Context Library (knowledge graph)
  • Orchestration (bundled framework)
  • CLI (developer tools)
  • Web Viewer (cards, plans, plays, team)
  • Agent Play (analytics, premium)
  • Settings (token modes, schedules)
  • Rules (franchise rules)
  • Cross-library data layer
  • Hosting (agents, skills, CLI)

Outside S

  • Model (Opus, Sonnet, etc.)
  • Sources (Notion, Slack, GitHub...)
  • Orchestrator engine (LangGraph, etc.)
  • Knowledge data layer (storage)
  • Version control (Git)
  • Harness (Claude Code, Codex, Pi)
  • Container / Sandbox
  • Factory (production facilities)

open question The precise boundary of S is not yet settled. Both co-founders agree on the general shape but the bottom-up exercise to draw the definitive line hasn't been completed.

Decisions

Platform Strategy

Multi-Model Architecture

settled

Alexandria must be multi-model. Cannot be all-in on any single provider.

  • Can have Anthropic-specific features (Claude plugin, agent SDK)
  • Can have provider-specific optimizations
  • Must not require exclusivity to any model

Supersedes Jess's earlier reflection suggesting "go all-in Anthropic." On further consideration: multi-model is the correct strategic position.

Storage Is an Implementation Detail

settled

The knowledge data layer is the most commoditizable component. We don't sell on storage.

  • Beadification is wise & practical engineering
  • Storage layer must be abstracted and swappable
  • Like which database a SaaS app uses — matters for performance, not for the pitch
  • We own retrieval logic and card schema, not storage

Beadification roadmap updated. Decision 22 (Beads) reframed.

Direction

Federation

A company is a group of federated libraries

  • Cross-library data layer is a core inside component — settled as architectural direction
  • Implementation is deferred — don't need to build this yet
  • Every library is a franchise. When we learn something, every franchise gets better.
  • A company = product library + company library + potentially more
  • Danvers is currently building the Alexandria Company library as a separate, linked library
"We don't need to build this yet, but need to know that federated is where we're going."
— Jess, classification

S/S'/S'' Staged Expansion

settled (architecture)

S — agents + plays + context library + orchestration. The tight core.

S' — orchestration integration, hosted viewer, agent play

S'' — full hosted app, cross-model, SOC 2, enterprise, talent marketplace

"Architect S such that we could do S' and S''. Build for acquisition by pointing to S'/S'' and saying: the bigger value is here."

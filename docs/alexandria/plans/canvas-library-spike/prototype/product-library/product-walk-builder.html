Atlas Studio — Product Walk

Drafted from Tour + Day-in-life + Loose ends · Read cold, redline freely, approve when ready

1 · What Atlas Studio is

Atlas Studio is a workspace product for small operating teams. The shipped entry today is /atlas — it opens the project workspace, initializes if needed, or returns the operator to their existing configuration. The product is built on three coordinated surfaces: a Workspace where items are created and worked, a Detail view for zooming into a single item, and an Activity feed that mirrors recent changes. Sharing controls branch off the Detail view; Settings is the admin surface.

Behind the scenes: a notification fan-out service runs on-event, and a search index refresh runs nightly. Neither is operator-facing.

2 · The operator's day ●

An operator typically opens the Workspace first, scans their item list, and starts working what's most active. Mid-morning is when collaborators tend to come in — sharing flows and activity feed activity spike. Mid-afternoon is the focus stretch; evening cleanup lands the operator on Settings or the Activity feed for a quick scan.

Three sources of work move through the day: scheduled (nightly index refresh), reactive (notifications fan out when items change), and ad hoc (operator creates, edits, shares).

3 · Forward plan ●

Near-term, multi-user editing on inline fields is the next planned capability (Q3). Workspace search across projects is on the considered list. Mobile is not on the roadmap.

4 · Loose-end answers

  • Queue items? No queue today. Operator-driven; reactive notifications only.
  • Splash analysis? Not built. Atomic linkage of references hasn't been a priority.
  • Bench / agents? Single-operator product; no agent roster.
  • Settings gate semantics? Standard admin — no approval gate.
  • Name "feed" vs "stream"? Feed wins. Vocabulary decision.

5 · Open questions Raven has

  • Is "item" the right shared noun, or are there distinct kinds?
  • How does Sharing relate to Workspace permissions?

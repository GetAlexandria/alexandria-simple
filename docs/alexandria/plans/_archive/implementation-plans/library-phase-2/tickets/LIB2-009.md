## Motivation

Phase 2's exit criterion from the vision doc: "Can Raven complete a full library initialization — configuration, gap analysis, assessment document — through conversation, with Sam producing the artifacts, and the scoreboard updating, without the user ever seeing a step-number or a form?"

This ticket is the human-run validation that answers that question. Code that compiles is not done. A conversational workflow that has never been run end-to-end is not done.

## Description

Run `/library` through at least two full initialization scenarios manually. Document what happened, what worked, what didn't, and what needs follow-up.

**Scenario 1: Greenfield initialization**
- Start: empty project, no alexandria-config.json, no library cards, no source material
- Expected: Raven opens with first-five-minutes sequence, conducts configuration conversation, directs Sam to produce Vision card and alexandria-config.json, renders scoreboard, issues stopping-point clearance
- Verify: scoreboard renders correctly, alexandria-config.json is schema-valid, assessment.md exists, no step numbers or form fields appeared

**Scenario 2: Returning session with prior state**
- Start: project with alexandria-config.json from Scenario 1, some cards produced
- Expected: Raven reads current state, renders scoreboard, surfaces delta ("here's what changed"), asks what to work on, continues conversation from where Scenario 1 left off
- Verify: scoreboard reflects current library state accurately, Raven does not re-ask settled configuration questions

**Optional Scenario 3: Brownfield with existing docs**
- Start: project with existing documentation (README, design docs, etc.) but no alexandria-config.json
- Expected: Raven reads available material, infers configuration where possible, asks only what cannot be inferred
- Verify: inference is surfaced explicitly ("I'm reading your README as High novelty — does that feel right?"), not silent

**What to document:**
- Any session where Raven broke character (gave step numbers, asked form-style questions)
- Any scoreboard rendering issues
- Any Sam artifact quality issues (alexandria-config.json schema errors, malformed cards)
- Any session-start failures (wrong orientation, missed state changes)
- Any stopping-point calls that felt wrong or unhelpful
- What felt good — moments of genuine Raven-as-guide experience

**Follow-up tickets:**
If issues are found, open follow-up tickets for each distinct problem. Do not fix issues inline during the smoke test — document first, fix separately.

## Context

Eval strategy from the vision: "Build it, play with it, then harden." This ticket is "play with it." The hardening (eval case design, LLM-as-judge coverage) comes in a later phase based on what actually breaks during play. The smoke test is not a replacement for eval coverage — it is the prerequisite for knowing what to cover.

## Acceptance Criteria

- [ ] Scenario 1 (greenfield) completed and documented
- [ ] Scenario 2 (returning session) completed and documented
- [ ] Documentation captures: what worked, what broke, what felt off
- [ ] alexandria-config.json from Scenario 1 passes schema validation
- [ ] assessment.md from Scenario 1 exists and is structurally complete
- [ ] Follow-up tickets opened for each distinct issue found (if any)
- [ ] Smoke test results checked in as `docs/alexandria/implementation-plans/library-phase-2/smoke-test-results.md`

## Implementation Notes

Run the smoke test in a real project — not a synthetic fixture. Use a project where someone is actually building a product, or use the Alexandria repo itself (which has rich library state). The richer the library state, the more meaningful the returning-session scenario.

The smoke test is done by a human, not automated. Its value is the real-session experience: does Raven feel like a guide or like a form? Does the scoreboard feel trustworthy? Does the stopping-point call feel useful? These are judgment calls that cannot be automated at this stage.

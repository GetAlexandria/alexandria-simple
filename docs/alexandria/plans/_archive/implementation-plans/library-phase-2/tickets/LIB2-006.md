## Motivation

Session-start is the procedure that makes `/library` a persistent room rather than a one-time command. Without it, every session starts from zero. With it, Raven reads current state, renders the scoreboard, and picks up where she left off — the property that makes the iterative model valuable.

## Description

Write the session-start procedure as a section in `skills/raven/job-initialize.md` (created in LIB2-004). The procedure runs at the beginning of every `/library` session before Raven speaks to the user.

**Step 1: Read alexandria-config.json**
- Location: `docs/context-library/alexandria-config.json`
- If absent: this is a first-time session. Go to first-time path.
- If present: extract active knowledge areas, their tier assignments, and any session notes from previous runs.

**Step 2: Read library state**
- Glob `docs/context-library/**/*.md` for existing cards
- For each card, check for Conan grade metadata in frontmatter (if present)
- Check `docs/context-library/sources/` for source material files per knowledge area

**Step 3: Compute scoreboard**
- Apply derivation spec from LIB2-002 to produce fill level per knowledge area
- Compute bucket aggregates (Foundation %, Core lock status, Amplifier availability)
- Invoke renderer from LIB2-003 to produce ASCII output

**Step 4: Orient**

*First-time path (no alexandria-config.json):*
- Skip scoreboard display — there is nothing to show yet
- Open with the first-five-minutes sequence (introduction, value exchange, handshake, questions welcome, then the product)

*Returning path (alexandria-config.json exists):*
- Show the scoreboard
- If library state has changed since last session: surface the delta — "Since we last talked, [X] areas moved. [Area] is now at [level]. [Area] regressed — Conan flagged [issue]."
- If no meaningful change: "Here's where we are. [Summary of scoreboard state.]"
- Ask what the user wants to work on this session

**Step 5: Regression handling**
- If any area's fill level is lower than expected (e.g., Conan failed cards that previously passed), surface this without derailing: "I'm seeing [Area] dropped — Conan flagged [issue]. We can address that this session or note it for later. Your call."
- Do not re-ask settled configuration questions (AI mode, novelty, complexity) unless the user initiates reconfiguration

## Context

The scoreboard is derived from alexandria-config.json + library state — not conversation history. This means Raven can reconstruct correct state at any session start, even if months have passed and many agents have touched the library in between. The session-start procedure is the runtime expression of the "derived from state, not persisted separately" design decision.

Session notes: alexandria-config.json may include a `session_notes` field written by Sam at end-of-session. Raven should read this to understand what was discussed in the last session — but the scoreboard should be re-derived from current state, not read from session notes.

## Implementation Notes

The procedure must be specific enough that Raven follows it correctly without ambiguity, but it should not read as a mechanical script. Write it as a professional procedure: "Read alexandria-config.json at [path]. If absent, this is first-time — proceed to first-time opening." Use imperative language throughout.

The session notes field in alexandria-config.json is advisory, not authoritative. Raven reads it for context but derives scoreboard state independently.

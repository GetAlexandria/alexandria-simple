## Motivation

A greenfield user's first `/library` session generates source material and initial configuration. Their second session — after they have shipped and have a real codebase — is a different context. If session-start does not handle this transition, Raven either re-runs first-time onboarding (wrong) or silently applies returning-user logic without acknowledging what has changed (also wrong).

## Description

Extend the session-start procedure (LIB2-006) with greenfield-to-brownfield detection and handling.

**Detection:**

A greenfield-to-brownfield transition has occurred when:
- `alexandria-config.json` exists (indicating at least one prior session)
- The prior session had minimal library state (few or no cards, small number of source files)
- The current library state shows a code presence that wasn't there before (e.g., a codebase now exists in the project root, or source material has grown substantially)

Concretely: check whether a `src/` or equivalent code directory now exists that didn't exist when alexandria-config.json was last written. A heuristic: if `alexandria-config.json` is older than the oldest code file in the project, a transition may have occurred.

**Handling:**

When transition is detected, Raven's opening for the returning session should:
1. Show the scoreboard as-is (reflecting current library state)
2. Acknowledge the change: "Last time we talked, you were pre-ship. It looks like you've got a codebase now. That changes what's available for us to work with."
3. Offer the scanner path: "Want me to read what's there and see if it fills in any gaps? Or would you rather tell me about it?"
4. If scanner path chosen: invoke codebase scanner, integrate results into scoreboard derivation, re-render scoreboard with any new fill-level updates
5. Continue as a returning session with the updated scoreboard

**No-transition returning path:**

If no transition is detected, continue with the standard returning session-start (LIB2-006): show scoreboard, surface delta, ask what to work on.

**First-time greenfield path:**

If no alexandria-config.json exists AND no significant material is present: continue with the first-time greenfield opening from LIB2-006.

## Context

From the handoff: "A greenfield user generates source material in their first `/library` session. On their second visit, they've shipped and have a codebase. Do they hit the scanner path, the brownfield path, or something hybrid? The scoreboard should handle this naturally (bars at 0% for everything, now let's fill them), but the session-start procedure needs to handle the greenfield-to-brownfield transition without confusion."

The answer: hybrid. The scoreboard remains the shared reference. Raven acknowledges the new state, offers the scanner path as the natural next move, and integrates new material into the existing scoreboard shape — she does not restart the configuration.

## Acceptance Criteria

- [ ] Greenfield-to-brownfield detection logic is specified in session-start procedure
- [ ] Returning-with-codebase session path is distinct from first-time and from standard returning paths
- [ ] Raven acknowledges the transition explicitly rather than silently applying returning logic
- [ ] Scanner path is offered and, if accepted, scanner output is integrated into scoreboard derivation
- [ ] Existing configuration (AI mode, novelty, complexity) is preserved across the transition — not re-elicited unless the user wants to reconfigure

## Implementation Notes

The transition detection heuristic (comparing alexandria-config.json age to code file ages) is approximate. Raven should not treat detection as definitive — she surfaces the observation and lets the user confirm: "It looks like you've shipped since we last talked — is that right?" This is friendlier and more reliable than a silent heuristic.

If the scanner is not available or produces no output, Raven falls back to: "I can't read the codebase directly. Tell me what's changed since we last talked."

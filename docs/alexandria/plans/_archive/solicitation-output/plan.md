# Solicitation & Output Layer — Project Plan

**Issue:** #7
**Goal:** Build the output layer that renders gap analysis results into a human-readable
assessment document with impact statements and solicitation prompts.

**Depends on:** Gap analysis engine (issue #5, done)

---

## Context

The gap analysis engine (Step 5 in the wizard skill) produces machine-readable scores and
sequencing in `wizard-config.json`. But it doesn't produce the human-facing deliverables:
the assessment document with impact statements and the solicitation prompts that help teams
actually fill their knowledge gaps.

This issue adds Step 6 to the wizard skill — the presentation layer that turns gap analysis
data into actionable output.

All 22 solicitation prompts (with mode variants) are already written in
`docs/wizard/phase-6-intake-engine.md`. The output template is defined in
`docs/wizard/intake-output-template.md`. This is primarily assembly work.

---

## Implementation

### Step 1: Add Step 6 to SKILL.md

Add a new step to `skills/wizard/SKILL.md` that runs after Step 5 (gap analysis). The flow:

1. Load gap analysis results from `wizard-config.json`
2. Generate impact statements for each gap
3. Select solicitation prompts (with mode variants) for each gap
4. Write the assessment document
5. Present summary to user

Step 6 runs automatically after Step 5 completes (no separate invocation needed). It can
also be re-run independently if the user wants to regenerate the assessment document.

### Step 2: Impact statement generation

For each gap (action != "none"), generate a mode-sensitive impact statement using the
templates from `docs/wizard/phase-6-intake-engine.md`:

**Foundation gap:**
> Without [area name], [when_missing effect]. At [mode], this means [mode-specific
> consequence]. This is a Foundation gap — other knowledge areas depend on it for
> coherence. Seed this first.

**Core gap:**
> [When_missing effect]. For your [novelty]-novelty, [complexity]-complexity product
> at [mode] mode, this is a primary value driver — [mode-specific explanation].

**Amplifier gap:**
> [When_missing effect]. This area multiplies the effectiveness of your Foundation and
> Core knowledge. With [area name] in place, [specific amplification effect].

**Deprioritized gap:**
> [When_missing effect]. At your configuration, this is lower priority because [reason].
> Seed this after higher-priority areas are in place.

The `when_missing` text comes from the catalog in `wizard-engine.yaml`. The mode-specific
consequence is generated by combining the mode narrative risk with the area's role.

### Step 3: Solicitation prompt selection

For each gap, select the appropriate solicitation prompt from
`docs/wizard/phase-6-intake-engine.md`:

- Base prompt (all areas have one)
- Mode variant (some areas have Short-Order Cook, Pair Programmer, or Factory variants)
- "What good looks like" benchmark
- "Common pitfall" warning

Mode variant selection:
- If the area has a variant that matches the user's mode, use it instead of the base prompt
- Some variants cover multiple modes (e.g., "Short-Order Cook / Pair Programmer") — use
  these when the user's mode is listed
- If no variant matches, use the base prompt

The skill should reference `${CLAUDE_PLUGIN_ROOT}/docs/wizard/phase-6-intake-engine.md`
directly — the prompts are authored there, not duplicated into the skill file.

### Step 4: Write assessment document

Write `docs/alexandria/assessment.md` in the target project following the template
in `docs/wizard/intake-output-template.md`:

1. Configuration header (mode × novelty × complexity, pool size, gap counts)
2. Risk statement (from mode narrative in wizard-engine.yaml)
3. Seeding sequence table (phased, with impact statements)
4. Solicitation prompts section (one per gap, with benchmarks and pitfalls)

Only include phases that have gaps. Phase 4 (Already Covered) always appears.

### Step 5: Present summary to user

After writing the assessment document, present:

```
Assessment written to docs/alexandria/assessment.md

[N] solicitation prompts ready for:
- Phase 1 (Foundation): [list]
- Phase 2 (Core): [list]
- Phase 3 (Amplifier): [list]

Next: Work through the solicitation prompts with your team, starting with
Foundation gaps. Add responses to docs/alexandria/sources/ and then
ask Conan to inventory them.
```

## QA Plan

### Output format verification
- Run the full wizard flow (Steps 1-6) with a known configuration
- Verify assessment.md matches the template structure from intake-output-template.md
- Check: configuration header, risk statement, phased tables, solicitation section

### Impact statement verification
- Verify Foundation gaps include "seed this first" language
- Verify Core gaps reference the specific configuration (mode × novelty × complexity)
- Verify Amplifier gaps describe the multiplication effect
- Verify Deprioritized gaps explain why they're lower priority

### Solicitation prompt verification
- Spot-check 5-6 prompts against the spec in phase-6-intake-engine.md
- Verify mode variants are selected correctly (e.g., Factory variant used at Factory mode)
- Verify "what good looks like" and "common pitfall" are present for each gap
- Check that areas with no mode variant use the base prompt

### Mode variant selection
- Run at Factory mode: verify Factory variants are used where available
- Run at Pair Programmer mode: verify PP variants are used where available
- Run at No/Low AI mode: verify only base prompts are used (no mode variants)

### Edge cases
- All areas present+fresh: assessment should note clean bill of health, no solicitation section
- Single gap: assessment should still be well-formatted
- All areas absent: every area gets a solicitation prompt

### LLM-as-Judge evaluation
Following the qa-wizard.sh and qa-gap-analysis.sh pattern, evaluate:
1. Assessment document follows template structure
2. Impact statements are mode-appropriate
3. Solicitation prompts match the area (not generic)
4. "What good looks like" is actionable
5. "Common pitfall" is specific
6. Free of product-specific terminology
7. Comprehensible to a product person

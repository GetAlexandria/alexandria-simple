MAPPING TO DESIGN INTERVIEW DIMENSIONS

(1) GOAL — what a successful run produces / done-condition / what FAILED looks like

Successful run: A written, stakeholder-approved scope artifact containing — at minimum — a problem statement, hypothesis, MoSCoW-sorted feature list (Must/Should/Could/Won't), explicit out-of-scope declarations, success metrics, and effort estimates. Depending on method: a story map with a drawn horizontal release line (Patton), a Shape Up pitch with breadboards and a No-gos section (Singer), or a Prioritised Requirements List (DSDM).

Done condition: Stakeholder sign-off secured; team can re-state what is IN and what is OUT without referring to notes; at least one success metric is measurable; non-functional requirements have owners.

Failed run looks like: Must-Haves list is 100% of the feature set (no contingency buffer); scope is stated only in terms of features with no explicit out-of-scope list; no hypothesis or learning goal specified; stakeholders have not aligned; artifact is a list of desiderata rather than a cut scope.

(2) TRIGGER — when it fires / what must exist first

Fires when: a defined product idea or feature request exists and a delivery decision is imminent (budget commitment, sprint planning, shaping bet). Not before: problem is still being discovered (discovery precedes this). Not after: engineering has begun without a scope agreement.

Must exist first: A problem statement or use-case motivation; some version of user insight (personas, research, analogues); at least a rough sense of time/budget constraints (otherwise appetite cannot be set); stakeholders available for alignment.

(3) REQUIRED KNOWLEDGE — inputs needed / missing-input convention

Required inputs: Problem statement (1–2 sentences), user/persona data, business objectives or learning hypothesis, hard constraints (deadline, budget, regulations), competitive or current-state context. Optional but valuable: existing wireframes or pitch decks, prior usage data.

Missing-input convention (synthesized from practitioner sources): Block on missing problem statement — the session cannot produce a hypothesis without it. Proceed-degraded on missing user research — note the gap, flag risk, add an assumption log. Ask on ambiguous constraints (budget unstated, deadline TBD) — cannot set appetite without at least a directional number.

(4) GOLDEN PATH — ordered moves, smallest defensible steps

Step 1 — Problem alignment: Articulate the problem statement in one sentence. Confirm the learning hypothesis ("We believe that [user] who [does X] will [achieve outcome] because [rationale]"). Establish the appetite or time/budget constraint.

Step 2 — Backbone / journey mapping: Map the high-level user activities left to right (story map backbone) or the core user flow (Shape Up breadboard), without features yet. Confirm coverage is complete — every major step the user must take.

Step 3 — Feature generation: For each backbone node, brainstorm stories/features without prioritizing. Goal: surface the full candidate set before cutting.

Step 4 — Prioritize using MoSCoW: Sort features into Must/Should/Could/Won't. Apply the 60% rule — if Must-Haves exceed 60% of effort, force a second pass. Apply Patton's scope-reduction lens: narrow the user population or problem set, not just trim features.

Step 5 — Draw the release line / write No-gos: In a story map, draw a horizontal line below the Must-Have row. In Shape Up, write the No-gos and Rabbit Holes sections explicitly. In a MoSCoW PRL, freeze the Won't-Have list. The artifact at this step is the primary deliverable.

Step 6 — Attach success metrics and done-condition: State what measurable signal proves the MVP validated its hypothesis. Define non-functional acceptance criteria.

Step 7 — Stakeholder sign-off: Confirm alignment. Treat the scope document as a living artifact with bi-weekly lightweight change control, not a carved-in-stone contract.

COMPOUND CANDIDATES

1. Problem Statement + Hypothesis Authoring — artifact: one-sentence hypothesis statement; fires at project kickoff before any feature discussion; evidence from Lean Startup (validated learning requires a stated hypothesis), Boundev 3-hour framework (hour 1), and Thinslices step 1–2.

2. User Journey / Backbone Mapping — artifact: story map backbone (left-to-right activity row) or Shape Up breadboard; fires after hypothesis is set, before any feature-level work; evidence from Patton (backbone is prerequisite to horizontal slicing), Singer (breadboarding precedes appetite allocation to solution).

3. Feature Brainstorm (Pre-Prioritization) — artifact: flat, unprioritized feature list per backbone node; fires after backbone exists; must complete before MoSCoW sorting; evidence from Cayenne Apps step 3, Boundev hour 2 silent brainstorm phase.

4. MoSCoW Prioritization Pass — artifact: four-column sorted feature list / Prioritised Requirements List; fires on an existing feature list with a known appetite; standalone because it can be re-run when appetite changes; evidence from DSDM Agile Business Consortium (project/increment/timebox levels), Boundev matrix output.

5. Release Line Drawing / Scope Cut — artifact: story map with horizontal line, or Shape Up No-gos + Rabbit Holes section; fires after MoSCoW pass; the literal "cut" moment; evidence from Patton (horizontal line as primary MVP demarcation), Singer (No-gos as standalone pitch section), Cayenne Apps step 5.

6. Smoke Test / Pre-Build Validation — artifact: experiment report (e.g., AdWords test, landing-page test, Wizard of Oz); fires after scope is defined but before engineering commitment; can substitute for or follow MVP build; evidence from Ries ("simple AdWords smoke test" to disprove hypotheses before building).

7. Success Metrics Definition — artifact: metrics table with measurable targets (DAU, Day-7 retention, conversion, NPS); fires after scope is cut; could run in parallel with release line drawing but requires hypothesis clarity first; evidence from Boundev (success metrics as separate deliverable), Thinslices step 8.

DESIGN-INTERVIEW MAP

(1) GOAL
Successful run: A ratified, written scope boundary that specifies the single riskiest assumption being tested, exactly which features are in/deferred/never, an explicit "won't do" list with stakeholder sign-off, and a measurable done-condition (observable user behavior, not feature delivery).
Done-condition: Every stakeholder can name the one hypothesis being tested and the single success metric before build starts; the "Won't" list is documented and co-owned.
Failed run looks like: Teams start building before any hypothesis is named; stakeholders see the cut list for the first time mid-sprint; scope expands back toward the original full-product list; quality is silently degraded rather than scope reduced; or the shipped artifact cannot be demoed to a user to produce a reaction.

(2) TRIGGER
Fires when: A defined feature or product concept exists but its build cost significantly exceeds the appetite, OR there is pressure to ship "everything" in a first release.
What must exist first: A problem statement (not a feature list), a defined target user, a candidate set of features, and at least one named assumption whose failure would invalidate the concept. Missing-input convention: If no named hypothesis exists, block — scope cannot be cut until the learning goal is declared.

(3) REQUIRED KNOWLEDGE
Inputs needed: Candidate feature set, appetite/time constraint, identified riskiest assumption, stakeholder list (who must ratify cuts), and current-state baseline (what users have today, to enable "compare down" evaluation).
Missing-input convention: Missing appetite → ask (scope cannot be set without a time constraint); missing hypothesis → block (cutting scope without a learning goal produces cargo-cult MVP); missing stakeholder map → proceed declared-degraded but flag silent-cut risk explicitly.

(4) GOLDEN PATH
1. Name the single riskiest assumption and write it as a falsifiable hypothesis before touching the feature list.
2. Set the appetite (fixed time box); do not estimate first.
3. List all candidate features; mark each Must/Should/Could/Won't collaboratively with stakeholders present.
4. Apply scope hammer: for every Must, ask "Could we ship without this? What happens if we don't?"
5. Draw the vertical slice: confirm the cut set delivers an end-to-end observable user outcome (not a horizontal architectural layer).
6. Compare the remaining set "down to baseline" not up to the ideal.
7. Publish the Won't list as an explicit part of the plan with parking-lot criteria for when items will be reconsidered.
8. Ratify in writing with all stakeholders — silent cuts are prohibited; every deferred item is named and documented.
9. Establish a change-control tripwire: any post-ratification addition requires explicit scope-out of an equivalent item or timeline extension.

ROOT-CAUSE SYNTHESIS

ROOT CAUSE 1: No learning goal declared before scoping.
Effect: Any cut is arbitrary; the scope has no logical stopping point; the team has no filter to evaluate what belongs in the MVP vs. what does not. This is the source of cargo-cult MVP and phase-1-of-everything both.
Named counter-practices: Blank's "Hypotheses-Experiments-Tests-Insights" frame (steveblank.com); Ries's validated-learning definition as the unit of progress (theleanstartup.com); Kromatic's "an MVP is not learning" warning.

ROOT CAUSE 2: Fixed scope, variable quality (the Shape Up inversion problem).
Effect: Under delivery pressure, teams quietly reduce code quality, skip edge-case handling, and degrade performance rather than cutting features — because cutting features requires a hard stakeholder conversation that quality degradation does not.
Named counter-practices: Shape Up scope hammer + tilde marker (basecamp.com/shapeup ch.14); "compare down to baseline" mental model; appetite set before shaping.

ROOT CAUSE 3: Horizontal slicing — MVPs scoped by architectural layer rather than user outcome.
Effect: No individual slice produces observable user value, so there is nothing to demo, nothing to measure, and no validated learning until all layers are complete — at which point the cost of being wrong is maximum.
Named counter-practices: Vertical-slice INVEST criterion (humanizingwork.com); walking-skeleton approach (Agile Alliance/Jeff Patton lineage).

ROOT CAUSE 4: Silent cuts and no ratification record.
Effect: Stakeholders who were not party to the cut decision re-add features post-launch; cuts reverse; scope balloons back. Trust damage compounds because the PM appears to have changed commitments without warning.
Named counter-practices: Visible Won't list as plan artifact (EVNE Developers); parking-lot document with explicit reconsidering criteria; weekly real-build demos to stakeholders (not slides) to keep feedback evidence-grounded.

ROOT CAUSE 5: Customer extraction without customer value (the SLC/Cohen failure).
Effect: Users experience incomplete products and disengage or form negative brand associations; the "M" in MVP dominates and "V" disappears; even if the team learns, the business loses the trust capital required to iterate.
Named counter-practices: Cohen's SLC frame — every v1 must be independently lovable and complete for its narrow scope, not merely viable in an engineering sense (longform.asmartbear.com/slc).

RUBRIC SYNTHESIS: 6-10 yes/no eyeball checks a non-developer Director can run on a scope-cut artifact

1. HYPOTHESIS NAMED — Is there one written sentence stating what this build will prove or disprove (the value or growth hypothesis)? (Fail = no learning goal, just a feature list)
2. PROBLEM + SOLUTION PAIRED — Does the document show the specific customer problem AND the proposed solution together, not just a solution list? (Fail = solution without stated problem; shape up explicitly requires both)
3. NO-GOS EXPLICIT — Does the document contain a named list of things explicitly not being built in this version? (Fail = absence of boundary; "Won't-Have" column or pitch No-gos section required)
4. EVERY FEATURE TRACES TO HYPOTHESIS OR CORE TASK — Can each in-scope item be answered with "yes" to at least one of: does it test a risky assumption? does it let the user complete the core task end-to-end? (Fail = any item that cannot be traced)
5. WALKING SKELETON PRESENT — Is there a minimal end-to-end flow a user can complete — even clumsily — from entry to outcome? (Fail = the artifact covers only some layers, e.g., only the UI is described, or only back-end, with no mention of how the seam is crossed; or no user can complete the core job at all in v1)
6. BASELINE COMPARISON MADE — Does the document compare the v1 scope downward to what customers do today (workaround), not upward to a future ideal? (Fail = rationale is "this is better than a hypothetical perfect version" rather than "this is better than the current painful reality")
7. SCOPE IS DEMONSTRABLE — Could you demo the in-scope work in a single session — does a real user perform the core job from trigger to output? (Fail = the "product" is a set of infrastructure improvements or internal APIs with no user-visible behavior that can be shown)
8. RABBIT HOLES CALLED OUT — Are the known unknowns or risky technical areas named, even if not yet resolved? (Fail = document is uniformly confident with no areas flagged as uncertain; this signals shaping was not done deeply enough)
9. MUST-HAVES SEPARATED FROM NICE-TO-HAVES — Is there a formal split (tilde notation, MoSCoW bucket, or equivalent) distinguishing items that block shipping from items that can be cut if time runs short? (Fail = everything is listed as required)
10. TIME BOX MATCHES SCOPE SHAPE — Given the appetite (time budget), do the must-haves look completable without heroics — or does even a casual read suggest the list is too long for the window? (Fail = the must-have list obviously exceeds the time budget, or no time budget is stated at all)

COMPOUND CANDIDATES

1. HYPOTHESIS WRITING — Artifact: one-sentence hypothesis statement ("We believe [feature] will cause [outcome] for [persona]"). Fires: before any scope session begins, when a problem statement is proposed. Evidence: Lean Startup build-measure-learn framing; boundev.ai scoping workshop Hour 1 entry gate; Goji Labs checklist item 1.

2. APPETITE SETTING — Artifact: appetite declaration (e.g., "six weeks, standard team"). Fires: before shaping begins, when a problem is greenlit for investigation. Evidence: Shape Up chapter 3 "Set Boundaries"; appetite is the first constraint that shapes everything downstream.

3. STORY MAPPING SESSION — Artifact: two-dimensional story map with backbone (activities) and ribs (tasks), with release line drawn. Fires: after hypothesis and appetite are set, when a team needs to visualize the full problem space and cut a defensible release slice. Evidence: Patton (jpattonassociates.com); Allegro worked example.

4. SCOPE HAMMERING SESSION — Artifact: annotated scope list with must-haves and tilde-marked nice-to-haves. Fires: during or after initial scoping when the must-have list exceeds the appetite. Evidence: Shape Up chapter 14; scope hammer Medium essay; eight-question hammering criteria.

5. RABBIT HOLE REVIEW — Artifact: named list of known unknowns with disposition (resolved / explicitly cut / deferred). Fires: before a pitch is finalized or before a cycle begins. Evidence: Shape Up chapter 6 pitch ingredients; chapter 14 extension criteria (no extension if uphill work remains).

6. PITCH WRITING — Artifact: a written pitch document with five sections (Problem, Appetite, Solution, Rabbit Holes, No-gos). Fires: after shaping, before the betting table, to package a shaped idea for decision-makers. Evidence: Shape Up chapter 6; Basecamp's own pitch reference document.

7. MVP LEARNING GOAL TEST — Artifact: a completed "What does v1 prove?" statement, linked to a success metric. Fires: as a gate before build begins, to verify the scope cut is an experiment not just a reduction. Evidence: Lean Startup (Ries); boundev.ai final scope review gate; Goji Labs checklist.

8. WALKING SKELETON VERIFICATION — Artifact: a defined end-to-end flow that a user can run through, even clumsily, demonstrating all layers connect. Fires: as a scope review check before committing to a sprint plan. Evidence: Cockburn/Freeman-Pryce definition; Patton's story map "topmost stories"; Adzic's skeleton-on-crutches variant.

9. SCOPE INCREASE REVIEW — Artifact: answered six-question checklist (from Department of Product) before any mid-cycle scope addition is approved. Fires: when a new feature request arrives after a scope is locked. Evidence: departmentofproduct.com fetched checklist.
